1. Big picture

Oracle stays on‑premise. All exchange goes through TIBCO. Zoho never touches the database.

STC → Zoho (push / webhooks) Zoho → STC (after warehouse action)

2. Warehouse structure

Every transaction resolves to a location, a zone, and a bin. Integration only writes to RECEIVING bins.

Locations

Parent: STC warehouses (container, no bin tracking).

  • Solutions by STC — full bins (~3,488)
  • Upsource · Pulse · VAS
  • Solution Operation · STC Disposal

Each entity has its own vendor + customer (12 contacts).

18 zones per entity

Cities × pools × sub‑inventories:

  • Riyadh · Dammam · Jeddah
  • Standard · FreeStock
  • Project · Internal · Unused

Zone name = exact Sub Inventory dropdown value. Never use legacy “Receiving Zone / Receiving Area”.

Bins

RECEIVING: {City} - {SubInv} - RECEIVING

Shelf example: Riyadh - Project - MZNAC0100A

Integration → RECEIVING only. Shelf move = Move Order (manual, out of Phase 1).

How sub‑inventory becomes a bin

  1. City = Dammam if locator 4th segment is Dammam, else Riyadh
  2. Map Project → Project · InternalN/Internal → Internal · UnUsed → Unused
  3. Target = {City} - {SubInv} - RECEIVING

3. Inbound cycle (Purchase)

Four steps · two integration touchpoints · ASN becomes a Purchase Receive (no separate ASN object in Zoho).

Step 0 · Idle
1 AddPurchaseOrder STC → Zoho Creates PO (Issued) Stock: none
→
2 AddASN STC → Zoho PR Pending Approval Stock: none
→
3 Mezzan Approve In Zoho UI PR → Received Stock → RECEIVING
→
4 AddGRN Zoho → STC Fires on approval Callback

Press Play to watch data move through the purchase cycle.

Step 1 — Purchase Order

  • STC endpoint: AddPurchaseOrder
  • Zoho: Purchase Order · set status Issued (not Draft)
  • Intended Sub-Inventory mandatory at header
  • No stock movement

Step 2 — ASN → Purchase Receive

  • STC endpoint: AddASN
  • Creates Purchase Receive in Pending Approval
  • Locator must be per line (cf_storage_location)
  • Sub-Inventory mandatory · no stock posts yet

Step 3 — Approval gate (Mezzan)

  • ASN = goods are coming · Approval = physically arrived
  • Stock posts to zone RECEIVING bin
  • Batch created using Section 6 formula
  • Do not auto-approve

Step 4 — AddGRN to STC

  • Outbound POST after approval
  • Stock already posted at step 3
  • PO Number on receipt is native (from PO)
  • Receipt number auto-generated
Put-away (context only): After approval, stock sits in RECEIVING until Mezzan imports Move Orders onto shelves. STC locators do not map to MZNxxxx barcodes — only the person placing the carton knows the shelf. Outside Phase 1 API.

5. Outbound cycle (Sales)

SO → Package → Shipment shipped → Shipping Confirmation to STC.

Step 0 · Idle
1 AddSalesOrder STC → Zoho Sales Order / RFD Committed
→
2 Pick & Pack Mezzan Package Batch selected
→
3 Ship Mezzan Shipment Order Stock leaves
→
4 Shipping Confirm Zoho → STC On dispatch cf_batch_id

Press Play to watch the sales / dispatch cycle.

Step 1 — Sales Order

  • Endpoint: AddSalesOrder / CreateRFD
  • Dropdowns: Transaction Priority · Ship With Care
  • Stock committed, not dispatched

Step 2 — Package

  • Every item is batch tracked — picker selects batch
  • Many batches possible (one item can have 70+)
  • Serial tracking OFF — do not map serials

Step 3 — Shipment

  • When shipment is shipped, stock leaves
  • This is the operational “dispatch” moment

Step 4 — SendShippingConfirmation

  • Outbound POST to STC on dispatch
  • cf_batch_id on Shipment carries dispatched lot
  • Should always be populated (batch tracking ON)

7. Batch reference (agreed with STC)

{Date Received} - {Locator} - {Supplier Item Code}

03/03/2026 - 16602.31.41294.DB Schenker.00000 - 6536501-1

  • Spaced hyphen separator (supplier codes contain hyphens)
  • Build from line-level locator
  • Date dd/MM/yyyy · manufactured_date = same day as yyyy-MM-dd
  • Expect high batch counts (~2,000 across Solutions data)

8. Six Phase‑1 APIs

UAT host: apitest.stcs.com.sa · Specs: DBSchenker v4.3 · ERP-SupplyChain v3.1

EndpointDirectionCreates / action in ZohoKey notes
AddItemRequestSTC → ZohoItemSKU = STC item code · Supplier Item Code mandatory
AddPurchaseOrderSTC → ZohoPurchase OrderStatus Issued · Intended Sub-Inventory mandatory
AddASNSTC → ZohoPR Pending ApprovalLocator per line · no stock
AddGRNZoho → STCCallbackOn Mezzan approval
AddSalesOrder / RFDSTC → ZohoSales OrderPriority · Ship With Care
SendShippingConfirmationZoho → STCCallbackOn dispatch · cf_batch_id

Auth note (client meeting)

STC wants OAuth 2.0 Bearer webhooks — not simple Flow URLs or direct Inventory POST URLs. Inbound may need an API gateway in front of Zoho.

Out of Phase 1

  • POD · Move Order API · Returns/RTV
  • Stock snapshot · PO update/cancel beyond create

9. Open decisions & verification

Must be answered with STC before mapping is final.

D1

SO PO fields

Populate cf_po_number or cf_locator_po_number?

Recommend: STC poNumber → cf_po_number; keep locator PO separate.

D2

ASN locator

Does ASN carry locator per line?

Required: Yes — batch depends on line locator.

D3

Dropdown values

Priority & Ship With Care exact enums?

Expect: High/Medium/Low · Yes/No — normalise if needed.

Verification checklist (before calling an endpoint “done”)

  • Line-level CFs on every line (not only first / header)
  • cf_supplier_s_item_code on every line
  • Sub-inventory = one of 18 exact zone names
  • Stock lands in correct RECEIVING bin — never shelf locator
  • Batch matches spaced formula from line locator
  • Multi-line receipt with different locators tested
  • ASN = pending approval · zero stock movement
  • GRN only on approval · stock posts then
  • Correct PO Line Number api_name per module
  • Partial receipt → PO partially_received with correct balance
  • Verify in the organisation — not only HTTP 200
