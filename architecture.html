0. Open points (Mostafa review — before build)

Do not treat OAuth middleware or GRN locator as decided until the owners below confirm.

P1 · Internal

OAuth webhook layer = scope change

Token URL + four Bearer POST endpoints means a custom middleware service (TLS, hosting, monitoring, uptime, maintenance). That is not Zoho Flow and was not in the original plan.

If STC insist on OAuth: confirm with Waleed & Nesma first — cost, timeline, and who owns the production service change.

Until then: document both options — (A) Zoho Flow webhooks if STC accept, (B) OAuth gateway only after internal approval.

P2 · Ask Manish / STC

AddGRN storageLocation — what do we send?

v3.1 sample sends line-level storageLocation (e.g. A1-17-01). Our design posts stock only to RECEIVING bins; put-away is manual / outside Phase 1.

Open: send RECEIVING bin name, echo STC locator from ASN, or another value? Must answer before outbound GRN is built.

P3 · Ask Manish / STC · BLOCKER

D2 — ASN locator per line

v4.3 ASN sample may omit line locator; batch reference cannot be built without it. GRN sample proves STC use storageLocation in their model — confirm ASN will carry it (field name + sample).

Put P2 + P3 to Manish in one request.

P4 · Plan

Dates still missing

Manish asked for Development / SIT / UAT / cutover dates. Even indicative durations settle it. Add to revised plan and send.

P5 · Business

Item serialControl: "1"

Spec sample sets serialControl to 1, but Zoho org has serial tracking OFF. Do not drop silently.

If STC send serialControl on some items: confirm business rule (reject, ignore with log, or enable serial for those SKUs).

2. Solution pattern (simple)

STC / TIBCO
   │  POST JSON  (OAuth Bearer IF option B approved — else Flow webhook)
   ▼
Inbound receiver  (Flow webhook OR approved OAuth gateway)
   │  map fields (exact CF api_names)
   ▼
Zoho Inventory  (Item / PO / PR Pending / SO)

Mezzan: approve receive · pack · ship
   │
   ▼
Zoho Flow HTTP  →  TIBCO AddGRN / SendShippingConfirmation
   (storageLocation on GRN = OPEN — see §0 P2)

Inbound (STC → Zoho)

STC pushes Item, PO, ASN, Sales Order. We create Zoho records. Stock does not post on ASN — only after Mezzan approval.

Outbound (Zoho → STC)

AddGRN after Purchase Receive approved. SendShippingConfirmation after shipment shipped.

3. Build steps (follow in order)

  1. Lock open points (§0) — Waleed/Nesma on OAuth scope; Manish on GRN storageLocation + ASN line locator; serialControl business rule; publish indicative dates.
  2. Choose inbound receiver — Flow webhooks (original plan) or OAuth gateway only after internal approval.
  3. Connect Zoho Inventory — org id 150001417597. Write with exact CF api_names.
  4. Inbound mapping — Item → PO → ASN(PR Pending) → SO. Locator per ASN line once STC confirms. Batch on approval only.
  5. Approval trigger — on PR approved: Flow calls AddGRN with agreed storageLocation rule.
  6. Outbound ship trigger — on Shipment shipped: Flow calls SendShippingConfirmation with cf_batch_id.
  7. Retries & alerts — 408/409 retry 3×; 400/401 no blind retry; email alert after failure.
  8. UAT — run checklist; verify values in Zoho UI, not only HTTP 200.

4. Inbound APIs (STC → our webhooks)

Payload shapes from DBSchenker v4.3. STC will POST equivalent JSON to our OAuth URLs. Spec paths below are the reference shapes / old STC URLs.

API 1 · AddItemRequest

Creates / updates Item in Zoho Inventory

INBOUND POST Spec path: /tibco/dbschenker/v1/supply-chain/item-master

Headers

  • api_key · Client-Id · Sender-Msg-Id (unique per call)
  • Our layer: if Option B approved — Authorization: Bearer <access_token>. If Option A (Flow webhook) — secret URL; confirm with STC.

What we do in Zoho

  • SKU / item code = STC itemCode (searchable by name or SKU only)
  • Map supplierItemCode → cf_supplier_s_item_code (mandatory)
  • Batch tracking ON · Serial tracking OFF across the org
  • Open (P5): if STC send serialControl: "1", do not ignore silently — confirm business rule (reject / log-and-ignore / enable serial for those SKUs)

API 3 · AddASN

Creates Purchase Receive in Pending Approval — no stock yet

INBOUND POST /tibco/erp/supply-chain/v1/asnasn

What we do in Zoho

  • Purchase Receive · status Pending Approval
  • Sub-Inventory mandatory · stock target later = RECEIVING bin only
  • Locator per line → cf_storage_location (required for batch)
  • Line refs: vendor line, STC item, supplier item, project, release
  • Do not auto-approve

Note · BLOCKER (P3 / D2)

v4.3 sample may omit line locator — handbook requires locator per line for batch. GRN sample shows STC use storageLocation. Confirm with Manish that ASN carries locator per line (field name + sample) before building receive/batch logic.

6. Zoho mapping rules (do not skip)

Always

  • Org ID on every Zoho API call: 150001417597
  • cf_supplier_s_item_code on every line
  • Stock only to {City} - {SubInv} - RECEIVING
  • Batch: {dd/MM/yyyy} - {Locator} - {SupplierItemCode}
  • Verify CF values in Zoho UI after write

API name traps

  • Lines: cf_vendor_po_line_number
  • SO header / Shipment: cf_po_line_number
  • PR line locator: cf_storage_location
  • Wrong name = HTTP 200 + empty field
Out of Phase 1: POD, Move Order API, Returns/RTV, stock snapshot, PO update/cancel beyond create.

7. Error handling

HTTPMeaningOur action
200 / 201 (+ business success flag)OKLog · no retry
400ValidationAlert · fix payload · no blind retry
401AuthAlert · check api_key / Client-Id / Bearer
404URLAlert · verify endpoint
408 / 409Timeout / backendRetry up to 3× then alert

batchId must be unique. Duplicate batchId returns error.
