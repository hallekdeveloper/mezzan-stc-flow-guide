Zoho Inventory  ·  Organisation 150001417597  ·  prepared by Hallek ERP Consulting 
For: Mohamed Waqqas, Integration Development 
 
How to use this document 
This is the single reference for the integration build. It covers the warehouse structure the transactions operate 
within, the inbound and outbound cycles step by step, every custom field and why it exists, the STC API files 
and what each maps to, and the decisions still outstanding. 
It supersedes nothing — it consolidates. The field inventory workbook issued previously remains the searchable 
reference for api_names; this document explains what those fields are for and how the transactions behave. 
Read Section 5 before writing any mapping. Three fields carry identical on-screen labels but different 
api_name values depending on the module. Zoho accepts a payload containing a wrongly-named custom 
field, returns HTTP success, and silently discards the value. These failures do not surface in testing unless 
results are verified against the organisation. 
1.  Warehouse structure 
Every transaction resolves to a location, a zone and a bin. Understanding this first makes the rest of the 
document straightforward. 
1.1  Location hierarchy 
There is a parent location, STC warehouses, which holds the physical address and has bin tracking disabled. It 
is a container, not a stock-holding location. 
Beneath it sit six child locations, one per STC entity. Each has its own vendor and customer record — twelve 
contacts in total.

1.2  Zones 
Each entity carries eighteen zones: three cities (Riyadh, Dammam, Jeddah) × two pools (standard, FreeStock) 
× three sub-inventories (Project, Internal, Unused). 
The zone name is exactly the value the Sub Inventory and Intended Sub-Inventory dropdowns accept. A value 
outside that list is rejected. 
Each entity also carries three Zoho default zones created at setup, including a legacy “Receiving Zone” holding a bin 
called “Receiving Area”. That is not part of this design — never target it. 
1.3  Bins 
Every zone has one RECEIVING bin, named “{City} - {Sub-Inventory} - RECEIVING”. Physical shelf bins follow 
the same pattern with the locator appended, for example “Riyadh - Project - MZNAC0100A”. The spaces either 
side of each hyphen are part of the name. 
The integration writes stock ONLY to the eighteen RECEIVING bins. It never targets a physical shelf location. 
Movement onto shelves is a Move Order, performed manually by Mezzan, and is outside Phase 1 scope. Move 
Order is not a workflow-capable entity in Zoho and cannot carry custom fields. 
1.4  Resolving a sub-inventory to a bin 
City is Dammam when the locator's fourth segment is Dammam, otherwise Riyadh. Sub-inventory maps Project 
to Project, InternalN to Internal, Internal to Internal, UnUsed to Unused. Target bin is “{City} - {SubInv} - 
RECEIVING”.

2.1  Why the approval gate exists 
The ASN tells Mezzan goods are coming. The approval is Mezzan confirming they physically arrived. Stock 
must not post before that, or the system shows inventory that is not on the floor. Do not auto-approve or design 
around this. 
2.2  What happens on approval 
● 
Stock posts into the RECEIVING bin of the zone named in Sub-Inventory 
● 
A batch is created, with the reference constructed as described in Section 6 
● 
AddGRN fires back to STC 
PO Number on the receipt is native, inherited from the purchase order and locked. Receipt number is native and 
auto-generated on its own series. 
2.3  Put-away — for context, not for build 
Stock then sits in the receiving bin until Mezzan move it onto physical shelves by Move Order import. This is 
deliberate: STC locator values have no bridge to Mezzan's MZNxxxx barcodes, so nothing in STC's data can 
determine which shelf a carton belongs on. Only the person placing it knows.

3.1  Batch selection at picking 
Every item is batch tracked, so the picker selects which batch is being dispatched. This has an operational 
consequence worth knowing: because each distinct combination of received date, locator and supplier item 
code becomes its own batch, a single item can present a long list at this point. One item in the current data 
carries seventy separate batches. 
Serial tracking is OFF across the organisation. TrackSerialNumber is false on all items. Serial numbers are not part of 
any flow — do not map them. 
3.2  Reporting back 
cf_batch_id on the Shipment Order carries the dispatched lot back to STC. Since everything is batch tracked, it 
should always be populated.

4.  Custom fields — what they are for 
The field inventory workbook lists every api_name. This section explains why they exist, which is what 
determines correct mapping. 
4.1  The four STC reference fields 
STC asked that PO No, Line No, Project No and Release No be captured so they can track shipment, dispatch 
and reporting. These are held at LINE level, not header, because a single receipt can cover several PO lines

4.2  Locator 
cf_storage_location at Purchase Receive line level holds STC's locator. It exists at line level because STC 
locators vary per line — the second segment is a line sequence. The header fields cf_locator_full and 
cf_locator_location cannot represent a multi-line receipt. 
The locator is a five-segment string: Project . Line Number . PO Number . Location . Shipset Number. For 
example 16602.31.41294.DB Schenker.00000

5.3  Sales Order carries two PO number fields 
cf_po_number and cf_locator_po_number both exist on the Sales Order header. Which one the integration 
populates is an open decision — see Section 8. 
5.4  Discovering fields correctly 
Header and line fields live under different entity names. Querying list_custom_fields on the parent returns 
item_entity_fields empty, which is misleading — line fields live under the separate *_item entity. 
list_custom_fields_simple returns empty for line entities and cannot be relied on. 
 
6.  Batch reference construction 
Agreed with STC so they can see stock categorised by their own identifying information. 
{Date Received} - {Locator} - {Supplier Item Code} 
Example:  03/03/2026 - 16602.31.41294.DB Schenker.00000 - 6536501-1 
● 
Separator is a SPACED hyphen. STC supplier codes contain hyphens themselves, so an unspaced 
separator makes the parts ambiguous. 
● 
The locator goes in EXACTLY as STC supply it — full five segments, never shortened or parsed. 
● 
Build from the LINE-level locator, not the header. 
● 
Date is dd/MM/yyyy. The native manufactured_date field carries the same received date as yyyy-MM-
dd. 
Consequence: every distinct date/locator/supplier combination becomes its own batch. Expect high batch counts — 
roughly 2,000 batches across 782 items in the Solutions data, one item carrying 70.

9.  Verification checklist 
Before declaring any endpoint complete: 
● 
Line-level custom fields populate on EVERY line, not just the first — the commonest failure is a value 
landing on the header only 
● 
cf_supplier_s_item_code present on every line of every payload 
● 
Sub-inventory resolves to one of the eighteen exact zone names 
● 
Stock lands in the correct RECEIVING bin, never a physical locator 
● 
Batch reference matches the Section 6 format exactly, including spaced separators 
● 
Batch reference built from the LINE-level locator, tested on a multi-line receipt where locators differ 
● 
ASN creates a receipt in pending approval with no stock movement 
● 
GRN fires only on approval, and stock posts at that point 
● 
PO Line Number targets the correct api_name for the module under test 
● 
A partial receipt leaves the PO partially_received with the correct balance open 
Verify posted results against the organisation, not the HTTP response. A 200 does not mean the custom 
fields landed.
